# Mod review — 2026-07-02

Mod-code audit: new mod ideas, concrete fixes, and cross-mod compatibility. Findings below were spot-verified against the current tree; file:line citations point at the code in question.

## 1. New mod ideas

1. **Cellar/Preserve Tracker** — Track fermentation/aging items (wine, cheese, preserves) the way `CropOptimizer` tracks crop growth: a Harmony patch mirroring `CropGrowthPatch.cs`, plus a `CropHudView`-style overlay showing days remaining and a "ready" ping. Natural fit given the game's time-gated production objects and a proven pattern to copy. Medium complexity — mainly reflection to find the preserve/keg component fields.
2. **Relationship Dashboard** — A HUD/window (same IMGUI style as `GiftingAssistant/UI/GiftingWindow.cs`) aggregating NPC friendship levels, upcoming birthdays (via `BirthdayReminder`), and favorite-gift data (`BirthdayReminder/Data/FavoriteGiftStore.cs`) into one "who haven't I talked to this week" view. Could ship as a new `HavensAlmanac` panel via the existing `IModDataProvider` pattern rather than a standalone mod. Low-medium risk — read-only aggregation, no save-file ownership.
3. **Fishing Log / Tackle Advisor** — Companion to `TrinketFortune`: track per-fish catch counts/rarest catches, using the same `DonationHelper`-style soft dependency to SMUT for "needed for museum" prioritization, and suggest bait/rod loadout by time-of-day/weather. Additive to existing hooks (`TrinketFortune/Patches/FishingTrinketPatches.cs`, `DonationHelper.cs`) rather than new patch surface. Medium complexity/risk — needs a new save file, must follow `docs/ATOMIC_SAVE_POLICY.md`.
4. **Skill Point Planner ("Respec Simulator")** — Extend `HavensRespec` with a dry-run mode: simulate a profession-tree reallocation and show projected point cost/refund without committing, reusing the existing `SkillResetService.CaptureSnapshot`/`UndoLastReset` rollback machinery. Low risk — mostly UI work on top of an already-transactional core (`HavensRespec/UI/RespecController.cs:184-208`).
5. **Museum Wishlist Overlay for Shops/NPCs** — When browsing a shop or NPC gift list, show a "museum needed" badge via SMUT's `DonationManager.HasDonatedByGameId` — same integration point `MuseumTodoIntegration.cs` and `TrinketFortune/DonationHelper.cs` already use. Low complexity — a Harmony postfix on the shop UI render path plus `IconCache`, entirely additive and read-only against SMUT data.
6. **Mod Health Dashboard (HavenDevTools panel)** — Surface each mod's "health snapshot" line (per `docs/MOD_LIFECYCLE_AND_LOGGING_CONTRACT.md` §5) in one aggregated view via the existing `IDevToolsPanel`/`DevToolsRegistry` plugin architecture — turning the documented-but-unenforced diagnostics contract into a real dashboard, and a natural place to surface the version-skew risk in finding #4 below.

## 2. Fixes

1. **HIGH — TheVault: `VaultSaveSystem.Load()` never falls back to `.backup` when the primary file is simply missing.** `TheVault/Vault/VaultSaveSystem.cs:212-227` only checks `File.Exists(canonicalPath)`/`File.Exists(legacyPath)`; if neither exists it silently creates a brand-new empty vault and returns `true` (`:222-227`) — the `.backup` file is never consulted here. `Save()` renames the live file to `.backup` before moving the new `.tmp` into place, so a crash between those two steps leaves the live file absent while the real data sits untouched in `.backup` — which `Load()` will never find, silently wiping the vault on the next load+save. Contradicts the documented intent of `docs/MOD_LIFECYCLE_AND_LOGGING_CONTRACT.md` §2 and `docs/ATOMIC_SAVE_POLICY.md`.
2. **HIGH — Same bug class in SMUT: `DonationSaveSystem.Load()`.** `SunHavenMuseumUtilityTracker/Data/DonationSaveSystem.cs:51-55` returns a fresh empty `DonationData` immediately if `!File.Exists(filePath)`, without ever checking `filePath + ".bak"`. Backup is only consulted in the `catch` block when the primary file exists but fails to parse (`:73-91`) — not when it's missing outright. Same crash-window data-loss risk as TheVault above. By contrast, `SenpaisChest/Data/SmartChestSaveSystem.cs:130-152` and `SunhavenTodo/Data/TodoSaveSystem.cs:103-121` both check the backup path unconditionally regardless of whether the primary exists — that's the correct pattern and should be back-ported to TheVault and SMUT.
3. **MEDIUM — HavensBirthright: shop-discount prefix mutates the shared item object's `price` field with no restoration.** `HavensBirthright/Patches/EconomyPatches.cs:57-104` reads `itemInfo.price` via reflection, discounts it, and writes it back onto the same object instance passed into `Shop.BuyItem`. If that listing object is reused across purchases in a session rather than freshly constructed per transaction, repeated purchases would compound the discount since nothing restores the original price afterward. Worth verifying against game behavior and snapshotting/restoring price in a postfix if the object is shared.
4. **MEDIUM — HavenDevTools: hardcoded mod-version table will drift from reality.** `HavenDevTools/UI/DebugWindow.cs:72-87` (`_knownMods`) bakes in a literal `(guid, name, version)` tuple per mod and passes that hardcoded version — not the actually-installed `PluginInfo.Metadata.Version` from `Chainloader.PluginInfos` — into `VersionChecker.CheckForUpdate(...)` (`:938`). Any point release of another mod without a synchronized HavenDevTools release causes a false "update available" or a silently stale "up to date" report. Fix: read the version from `Chainloader.PluginInfos[mod.guid].Metadata.Version` at check time instead of a compiled-in literal.
5. **INFO — Several previously-flagged overhaul-plan concerns are already fixed:** SenpaisChest's `SmartChestSaveSystem.Save()` already guards against overwriting non-empty disk data with empty in-memory state, and integration disposal is clean (no double-subscribe); HavensBirthright's `RaceDetectionService.RetryRaceDetection()` already re-checks elemental/body mismatches; HavensRespec's `PerformReset` is already transactional (charges cost after success, rolls back via `UndoLastReset` on failure); TrinketFortune's `DonationHelper` already degrades cleanly to vanilla RNG when SMUT is absent.
6. **LOW — Use GiftingAssistant's and SunhavenTodo's save systems as the reference implementation** when fixing #1/#2 — both already check `.bak` independent of primary-file existence.

## 3. Cross-mod compatibility

**Contract 1 (FasterRaces ↔ HavensBirthright speed stacking) — verified correct.** `FasterRaces/Plugin.cs:93-103` exposes `IsSpeedBonusActive` (true only when the mod is enabled and its bonus > 0). `HavensBirthright/Patches/StatPatches.cs:45-83` reflects on that exact property, defaults to `false` (HB keeps its own bonus) on reflection failure, and gates both the base movement-speed bonus and the Amari Bird Tailwind ability on it. Harmony priorities are explicit and consistent: HB's patch runs first (`[HarmonyPriority(100)]`), FasterRaces' postfix runs later (`[HarmonyPriority(300)]`) — no double-stacking.

**Contract 2 (SMUT ↔ SunhavenTodo ↔ SenpaisChest) — verified correct.** The integration only exists when both peer GUIDs are present (`SenpaisChest/Plugin.cs:212-225`), subscribes/unsubscribes symmetrically to `DonationManager.OnDonationsChanged` in constructor/`Dispose()`, and sets `TodoItem.IconItemId`/`MuseumDestination` via typed properties rather than reflection — matching the documented contract. `DonationManager.HasDonatedByGameId` correctly requires all museum-item IDs mapped to a game item to be donated before reporting "donated," handling the duplicate-bundle-appearance rule.

**Additional risks found (not yet documented in `docs/COMPATIBILITY_CONTRACT.md`):**

1. **Harmony patch collision on `Shop.BuyItem`.** Both `TheVault/Plugin.cs:857-907` (`ShopPatches.OnBeforeBuyItem`, a `bool` prefix that can skip the original for vault-currency items) and `HavensBirthright/Plugin.cs:411-422` (`EconomyPatches.OnBeforeShopBuyItem`, a `void` prefix mutating `price`) patch the same three `Shop.BuyItem` overloads with no explicit `[HarmonyPriority]`/`Before`/`After` ordering between them. No crash results, but there's no documented ordering contract for this shared target the way there is for `GetStat` — worth adding to `COMPATIBILITY_CONTRACT.md`, alongside a note about fix #3 above.
2. **`InitializeAsOwner` is independently patched by 6 mods** (SunhavenTodo, BirthdayReminder, TheVault, HavensBirthright, GiftingAssistant, SMUT) as the standard "character loaded" hook. All are additive postfixes today, so risk is low, but it's undocumented — a future prefix that mutates player state here would have no ordering guarantee.
3. **Version-skew risk for `TheVault.Abstractions` consumers.** `CropOptimizer/Integration/VaultReflection.cs:15-52` dynamically loads `TheVault.Abstractions.dll` from the Vault plugin's own directory at runtime rather than a compile-time reference — a defensible soft-dependency pattern, but CropOptimizer's behavior against a newer/older `IVaultModApi` shape is untested at build time (the interface's own doc comment warns signatures "may version slowly; check mod update notes"). No compatibility matrix ties CropOptimizer's supported Vault version range to specific `IVaultModApi` members — worth adding to `docs/MAINTAINER_VERSION_DRIFT_CHECKLIST.md`.
4. **No shared config/save-key collisions found.** Each mod uses its own `Paths.ConfigPath` subfolder and its own `.cfg` migration helper — no cross-mod file-path or BepInEx config-section collisions.
